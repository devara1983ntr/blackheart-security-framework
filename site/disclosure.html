Security disclosure

Every known risk, written down.

Including the one that looks worst on a scanner and is not a defect. If a risk in this repository is not on this page or in the CHANGELOG, that is a bug in this page, not a secret.

Accepted risk

82 open alerts. All 82 are in one file.

Dependabot reports 82 open vulnerability alerts on this repository. Every single one resolves to the same path:

dependency-auditor / test-project / package.json 
skills/third-party/claude-skills/engineering/skills/
  dependency-auditor/test-project/package.json

2 critical · 36 high · 37 moderate · 7 low

That is a sample-web-app fixture belonging to the vendored dependency-auditor skill — a tool whose entire job is finding vulnerable dependencies. Its stale axios, nodemailer, multer, mongoose, lodash and jsonwebtoken pins are the test data. The skill needs something old and broken to demonstrate itself against.

Why it is accepted instead of patched

  1. Patching it would break the mirror. The 3,864 vendored files are byte-identical to upstream 19392f7a by design, and validate.py enforces that on every push. Editing this file would make BLACKHEART's copy silently diverge from the thing it is supposed to be an honest mirror of.
  2. Patching it would destroy the corpus. Remove the vulnerable pins and the dependency-auditor skill has nothing to demonstrate on. The defect and the fixture are the same thing.
  3. Nothing executes it. No lockfile is committed, there is no build step, and nothing installs or runs this project. It is data on disk, not code in a path.

Enforcement

Accepting a risk is only honest if it is enforced.

A silent "this isn't a real vulnerability" is indistinguishable from having ignored it. So the decision is written to .github/known-vulnerable-fixtures.json and a CI group holds the line.

The group fails if…

  • the registry is deleted
  • a registered entry stops being vendored
  • an entry loses its written reason
  • a Blackhearts-authored dependency manifest ever appears

That last one is load-bearing

The entire argument above rests on this repository declaring no dependencies of its own — it ships no build step, no bundler and no third-party runtime. So audit group 20 asserts that premise on every run rather than trusting it. The day someone adds a real package.json, the acceptance argument stops applying and the build says so.

Every failure mode was tested

A gate that has only ever been observed passing is decoration. Each of the four conditions above was reproduced deliberately — an authored package.json dropped in, the registry deleted, a reason stripped, a path re-pointed out of the vendored tree — and each one fails the build with a specific message.

The same rule, applied twice

Fix ours. Account for theirs.

This is not a new idea here. It is the rule that produced the 111 registered dead links, and it applies identically to vulnerabilities.

Blackhearts-authored

Fixed. 48 defective links in documentation this project owns were corrected. The 159-link problem is now 48 fixed and 111 registered, with the registry refusing to accept a new unregistered defect.

Vendored upstream

Not edited. 111 genuine defects inside byte-identical upstream files are individually registered in .github/upstream-link-defects.json, each with a reason. Editing them would break the mirror guarantee.

Same principle, same enforcement, one more surface: 82 alerts accepted with reasons instead of 82 silent patches that break the mirror or 82 alerts nobody looked at.

What this page is not

The limits of this assurance.

A clean scan is a coverage gap

Nothing here claims the vendored content is safe. The 3,864 mirrored files were verified byte-identical, not audited for correctness. A mirror guarantee is a provenance claim. It is not a safety claim.

Nobody has tested these skills against a live target

The work here is static analysis, controlled input, and policy review. No target was assessed, no credential was used, and no production system was touched. A finding is a hypothesis until it is demonstrated.

Report a defect responsibly through SECURITY.md. This framework is for authorized work only — systems you own or have written permission to test.
